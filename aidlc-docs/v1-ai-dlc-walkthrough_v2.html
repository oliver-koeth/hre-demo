Client narrative

AI-DLC is not better prompting. It is a governed lifecycle around AI-generated software.

AI-DLC is a governed delivery lifecycle, not a prompt library. The AI takes an intent, decomposes it into adaptive lifecycle stages, produces auditable artifacts, and halts for explicit human approvals at every gate. Compliance requirements are enforced through a first-class extension mechanism: opt-in policy modules inject binding rules into applicable stages, so compliance constraints become engineering constraints before a line of code is written. Only once stages are approved does the AI turn design into code, tests, runtime, and end-to-end traceability.

0. Concept

Which AI-DLC to choose?

"AI-DLC" is not one product; it is a fast-moving category of methods and tools for governing AI-driven software delivery, ranging from prescriptive spec-gated lifecycles to bare autonomous loops. The table below compares the options considered before choosing AWS Labs' AI-DLC as the basis for this walkthrough.

NameDescription
▸BMAD-METHOD Open-source, npm-installed framework built around a scale-adaptive loop (Clarify → Plan → Build/Verify → Learn) driven by specialized AI agent personas (product, architect, UX, dev, test) that produce durable planning artifacts carried across sessions. Small changes can skip straight to build; complex work gets a full planning ceremony, plus a "BMad Loop" mode that can build, verify, and retro an entire epic unattended. Works with most major coding agents and also ships as ChatGPT/Gemini web bundles.
▸GSD (Get Sh*t Done) Lightweight meta-prompting and context-engineering layer on top of an existing coding agent (Claude Code, Cursor, Copilot, etc.), built to fight "context rot" via a repeatable Discuss → Plan → Execute → Verify → Ship loop. Delegates research, planning, and execution to fresh-context subagents and persists all state as plain Markdown/JSON in a .planning/ directory, with dependency-aware parallel "wave" execution of independent tasks.
▸Spec Kit (SpecKit) GitHub's official toolkit for Spec-Driven Development, where the specification generates the implementation rather than just guiding it. A gated slash-command pipeline (constitution → specify → clarify → plan → tasks → analyze → checklist → implement) works across 30+ coding agents, with extensions, presets, and role-based bundles for compliance, PM, or security personas. Currently the most widely adopted framework in this category by GitHub star count.
▸Ralph Not a tool but a technique for fully autonomous, unattended coding: a bash loop that repeatedly feeds the same prompt file to a fresh agent invocation, using each iteration's output (broken or not) as the next iteration's starting point. Relies on one narrow task per loop, a self-rewritten fix_plan.md, parallel subagents for search/write work, and tests/types as "backpressure" against bad generations. Best suited to greenfield work under senior-engineer supervision.
▸AI-DLC (AWS Labs) AWS's methodology-first approach (instruction/rule files, not a CLI) that plugs into whatever coding agent is in use. Structures work into three adaptive phases — Inception (what/why), Construction (how), Operations (run) — executing only the stages that add value, gating each stage behind explicit human approval, and writing every artifact to an auditable aidlc-docs/ folder. Supports opt-in compliance extensions (security, resiliency, DORA, property-based testing) as binding, blocking rules. This is the framework used for this walkthrough.
▸Gas Town A multi-agent orchestration and workspace manager rather than a prescriptive lifecycle — it complements frameworks like AI-DLC or BMAD instead of replacing them. Coordinates many concurrent coding agents across projects using git-backed worktrees ("Hooks"), a Mayor/Rigs/Crew/Polecats taxonomy, a bisecting merge queue so agents never push directly to main, and a tiered watchdog chain for reliability at scale.
▸Superpowers A composable Claude Code / multi-agent skills plugin implementing a full TDD-first methodology: Socratic brainstorming and design sign-off before any code, bite-sized plans executed by fresh subagents under git worktrees, strict red-green-refactor test-driven development, and mandatory two-stage code review. The single most-starred project in this category.
▸OpenSpec Brownfield-first spec-driven development: each change gets an isolated proposal/spec/design/tasks folder so concurrent changes never collide, in contrast to more rigid phase-gated approaches. Commands cover explore → propose → apply → archive, with a "fast-forward" mode to generate all artifacts at once and optional cross-repo shared spec stores.

1. Method

AI-DLC turns intent into a lifecycle, not a chat transcript.

The paper frames AI-DLC as a shift from AI-assisted coding to AI-driven lifecycle orchestration: humans set the intent and validate gates; AI proposes plans, decomposes work, generates artifacts, and carries context forward.

Reimagine, not retrofit

AI-DLC is designed for AI-native iteration cycles measured in hours or days, not a traditional SDLC with a coding assistant added at the end.

Reverse the conversation

The developer does not keep asking for isolated code snippets. AI asks clarifying questions, proposes stage plans, and makes trade-offs explicit for approval.

Design is core

Requirements, stories, domain decomposition, NFR design, architecture, and testing become first-class artifacts, not optional notes around generated code.

Humans validate gates

Human oversight acts as an early correction mechanism: approve, amend, or stop before downstream code and tests cement a wrong assumption.

Artifacts become memory

Every stage persists context in `aidlc-docs`, so the next stage reads approved requirements, stories, designs, and constraints instead of relying on prompt history.

No hard-wired path

Some stages are mandatory; others execute only when the request, complexity, risk, and workspace state make them useful.

2. GitHub implementation

In this repo, AI-DLC is enforced through Copilot instructions and rule files.

The mechanism is deliberately simple: `.github/copilot-instructions.md` overrides default software-development behavior, resolves `.aidlc-rule-details`, loads common rules, scans extensions, and writes all lifecycle evidence under `aidlc-docs`.

Execution contract for the assistant

  • Always start software development with workspace detection and audit logging.
  • Read the detailed rule file for the current stage before acting.
  • Create stage plans and generated artifacts in the prescribed locations.
  • Wait for explicit human approval at stage gates before continuing.
  • Keep `aidlc-docs/aidlc-state.md`, plan checkboxes, and `aidlc-docs/audit.md` synchronized.

Why this matters for Copilot users

Copilot in VS Code can produce code from local context. AI-DLC adds a delivery wrapper: stage discipline, rules, audit, quality gates, and traceability.

3. Extension mechanism

Extensions make the lifecycle policy-aware without loading every policy all the time.

The instructions scan an `extensions/` directory for lightweight opt-in prompts. Full rules are loaded only when the user opts in. Enabled rules become hard constraints for applicable stages. The extension model is the bridge from “developer asks Copilot for code” to “organization governs AI-assisted delivery”: it lets compliance, resilience, security, or domain standards become stage-specific gates instead of after-the-fact reviews.

How extension loading works

  • At workflow start, scan extension folders recursively.
  • Load only `*.opt-in.md` prompts initially.
  • Present opt-in choices during requirements analysis.
  • Load the matching full rule file only after opt-in.
  • Record enabled/disabled status in `aidlc-state.md`.

4. Tests

Testing is generated as part of the lifecycle, organized by purpose.

AI-DLC separates tests by purpose: unit behavior, property/invariant checks, cross-unit conformance, HTTP API integration, executable performance baselines, and future security/continuity testing.

TypePurposeConcrete examplesTest data shape
Unit tests Verify focused domain and persistence behavior. `Login_ShouldIssueToken_ForValidCredentials`, `Save_With_Stale_Version_Should_Return_Conflict` Users, roles, permissions, repository records, version metadata.
Property-based / invariant tests Validate repeatability and invariants across state transitions. `DisableUser_ShouldBeIdempotent`, retention deterministic outcomes. Repeated calls, unchanged state, valid and invalid windows.
Cross-unit conformance Ensure contracts are consistent across CoreSecurity, Governance, and Integration. RFC7807 problem details with `errorCode` and `correlationId`. Representative error responses and missing-field blockers.
HTTP integration Exercise the full ServiceHost over real HTTP without Docker. Login, token validation, MFA, user admin, audit, evidence, incidents, backups, OpenAPI. Isolated temp stores, generated AES/HMAC keys, request JSON payloads.
Performance tests Measure local latency, concurrency stability, throughput, failures, and GC deltas for performance NFRs. `NFR_PERF_001_AuthorizationEvaluate_ShouldStayWithinLocalLatencyBudget`, `NFR_PERF_003_HealthEndpoint_ShouldHandleLightConcurrencyWithinBudget` Release build, in-process ServiceHost, generated temp policy/secrets, JSON telemetry in `PERF_RESULTS_DIR`.

5. Build

Tests and build are consolidated by a single build-and-test gate.

Restore, build, and test all units in one deterministic sequence, then publish auditable instructions and telemetry artifacts for the quality gate.

Build stages

  • Restore dependencies with `dotnet restore AuthModule.slnx`.
  • Set optional `POLICY_CONFIG_PATH` for local config.
  • Build all units with `dotnet build AuthModule.slnx --no-restore`.
  • Run unit test projects across Foundation, CoreSecurity, Governance, Integration.
  • Run HTTP integration tests through `AuthModule.ServiceHost.Tests`.
  • Run performance tests from `tests/AuthModule.ServiceHost.Tests/Performance/` in Release mode with `PERF_RESULTS_DIR` telemetry output.

6. Compliance

Compliance evidence is generated from repository artifacts, stamped, and attested by the CI pipeline.

The DORA Compliance extension enforces a continuously maintained position paper. The document is scoped to development and local integration; operational sections are explicitly bounded. Each successful security scan refreshes the document, appends a run log entry, updates an integrity stamp, and produces a GitHub artifact attestation for the evidence.

DORA compliance document

The living position paper lives at aidlc-docs/compliance/dora-compliance.md. It is bootstrapped from the extension template and is governed by the DORA rule file.

  • Scope boundary: development and local integration testing only. Any section covering operational monitoring, incident response, BCDR, third-party ICT risk, or production data protection is marked with the exact phrase will be provided by operations.
  • Control mapping matrix: maps DORA-style control IDs to implementation summaries and evidence file paths or workflow names.
  • Gap register: tracks open gaps with owner, status, target date, and dependency, consistent with the operations-boundary markers.
  • Evidence index: links directly to CI workflows, traceability docs, build/test summaries, audit timeline, and state tracking artifacts.
  • CI security scan run log: appended automatically after every successful Security Scans workflow run with timestamp, run ID, attempt, result, and direct URL.
  • Integrity stamp block: contains repository, branch, 40-character commit SHA, document SHA-256 (body only, excluding the stamp section), UTC generation time, and generator identity.
